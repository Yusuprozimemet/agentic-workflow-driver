A script that runs AI coding work one step at a time

The whole project in eleven graphs, each answering one question. Point at, tap or tab to any mark, and the box under its graph says the detail. Every graph keeps its exact numbers in a table under it.

Day
A numbered step of the plan, written as a spec before it is built. It is not a calendar day: several Days can fit in one date.
Date
A calendar date, on the maintainer's clock.
Close
The last pull request of a Day. It ticks each promise with its evidence, and the costs are counted then.
The kit
The way of working this script automates, and the project it was started from. Its figures, reached with a person driving every step, are the baseline.
Main session
The AI conversation that does a step. The auditors and the implementer are separate AI agents it starts.
Gates
The checks work must pass: the auditors, a test seen failing, a break on purpose, the close and the evidence replay.
Hooks
Small scripts that refuse a call that breaks a rule, or cut a long output short.
The stop
A point the plan names where the work halts until the maintainer says to go on.

    Graph 10

    Where does a date's time go, and who waits for whom?

    One date on the clock. Each lane is one actor, and a bar is a stretch it was busy: a session writing or waiting on a command it ran, a pull request waiting to be merged, its checks running, the maintainer merging. The marks inside a session's bar are its waits of a minute or longer. Only this repository's sessions are drawn, and the maintainer's own reading and typing leave no mark, so a gap in a lane is not a rest. The sessions are counted on the maintainer's computer and end at the last count, which the readout names; the pull requests and checks come from GitHub and go on after it. A Day button above turns the clock to that Day's last date; the dates here pick another.

        How this works: follow one promise

        Every Day of work here is written down before it is built. The written version makes promises: single sentences saying what the software must do. Each promise then has to survive a series of checks, some by AI reviewers with no stake in it and some by a person.

        The names on the arrows describe the usual process for any Day. They are not a record of who did what on this one pull request.

        Written down firstTried on the codeChecked afterwards

        When something is wrong, the work goes back

        An auditor finds the spec is wrong

        The spec is corrected in its own pull request before any code is written.

        A test never failed

        A test that has only ever passed proves nothing, so it has to be seen failing before its pull request is opened.

        A later Day changes the behaviour

        Its spec names the old promise on a Replaces: line, and the old one stops counting.

        A step needs a person

        The driver parks: it opens an issue saying why and stops until the maintainer closes that issue. It does not guess.

        Who does what

        Each reviewer is a separate AI agent that starts with no memory of the work, so the session that built something is never the only one checking it. Select one to see where it acts.

        Built by scripts/spec-drift.py --build from git and GitHub at every merge. The token, refusal and gate counts come from scripts/token-usage.py, run on the maintainer's computer at each Day's close. The page this one replaced, with its sixty panels, is the tag dashboard-v1.
