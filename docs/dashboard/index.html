Summary

This project builds a script, run-steps.py, that runs a software project's AI coding work one step at a time, each step in a fresh Claude session. The aim is that a person stops approving every pull request and instead owns the plan, the safety checks and anything the script stops on.

Running this work by hand means a person typing “start Day N”, pressing merge, typing “merged” and opening a new session, over and over. The script is being built to do that repetition. The current phase builds the part that starts each step, and the maintainer still merges. Writing the plan and owning the checks stay with a person at every level.

How this works: follow one promise

Every day of work here is written down before it is built. The written version makes promises: single sentences saying what the software must do. Each promise then has to survive a series of checks, some by AI reviewers with no stake in it and some by a person.

The names on the arrows describe the usual process for any day. They are not a record of who did what on this one pull request.

How this is counted

For each finished day: of its ticked criteria, how many cite the PR they landed in, name a test, and record a break seen red in a broken: line. Each named test is looked up on main. CI runs every test that is there, so a criterion goes quiet only when its test leaves the tree or can be skipped (a test run on a system property runs when a workflow passes the property as true). A test that moved is followed under its new name, of the same stem or listed by the PR that moved it. A name counts only if it was in the tree when the day's last PR merged. Grey is retired: a later day's spec names the test and that day's PR removed it; orange is gone with no spec saying so. Days marked pre-format were written before the evidence format: nothing asked their ticks to record any of this, so a zero there is not measured, not missing. If the broken: line was asked for only from a later PR, “Seen red” is not measured for a day none of whose PRs reaches it.

What scripts/close-evidence.py --all, run by the dashboard workflow before each build and never committed, found when it replayed each finished day's evidence on main: the named tests looked up, the Verify commands run, the recorded breaks applied. The page build reads that report and runs nothing. “Failure recorded when built” above counts the broken: and seen-red lines a day recorded; here a break counts as passed only if it reported what its line says. A share is passed over passed, failed and errored, with the not-applicable beside it; a day checked at another close, or on a spec or breaks file main has since changed, is stale, not a pass.

Do the promises still hold?

We re-run each finished day's tests on the merged code and put back the bugs they were shown to catch.

How this is counted

Each finished day promised things the software must do. We re-run those tests on the merged code, and put back the bugs they were shown to catch. One square is one promise; open a feature to read its promises. “Planted bug caught” is the strongest of the three measurements on this page: “evidence on record” reads the spec, “failure recorded when built” reads a line in the spec, and this one re-runs the bug. The re-check is run by hand (scripts/replay-history.py), so it can be behind the latest change.

How this is counted

The greps a finished day's criteria or Verify say must print nothing, run over the tree at every merge from the day's end, from the root or a directory under verify_bases in spec-drift.config.json, wherever their paths are. Paths follow the directories that moved since (its moved), because a grep of a path that is gone prints nothing too. CI runs none of them. A check is orange when it finds lines on main, listed under it; grey when it reads no files; green otherwise. Since is the merge where that state began.

Hand-offs to days not yet run

What finished days leave for later: a Notes item that names a day not yet run, or a code comment that does ("Day 12 adds this"). Nothing else carries them forward. A Notes item with an ID (like H12.1) counts as picked up only when the receiving spec cites the ID; one without, when it names the day the item came from; a comment, when the spec names its file. Days in run order; a spec written in full should leave none open. Last: ID'd items no later day picks up, and tracks a PR announced that no branch ever named.

A merge with no spec name in the code has no gap angle and is left off the line.     What the vectors say

    How the vectors are built

    Snapshots. The initial commit plus every first-parent merge on main (). Code PRs, spec-change PRs and close-the-day PRs are told apart by branch name and title.

    The spec–code name gap needs a space both sides share. It is built from the code-like names the specs put in backticks. The spec vector counts how often each name appears in the specs. The code vector counts how often it appears in the code, with Markdown, data/, screenshots and comment lines left out: a comment naming a thing is not the thing. Both are log-scaled and compared by angle. Each merge’s gap uses only the names the specs had used by that merge, so a name a later spec adds does not move an earlier point. Counts are never negative, so even unrelated vectors sit well under 90°: the same code counts shuffled across the names would read today. With no spec name in the code there is no direction to compare, so no angle, rather than 90°. The other direction is counted apart: names the specs once used and have dropped, that the code still has. The gap is worth reading only as its distance from that value, so the chart draws the gap minus it: chance is the dashed zero line, and the band moves with it. The class lines under the cover chart show what the names are made of; the share of reached names found in the code (“The sawtooth, up close”) is the plainer measure.

    Where the work went counts git diff --numstat between one merge and the one before it, every file, so nothing merged is counted twice and nothing is left out. A moved file counts only the lines that changed in the move, under the path it moved to. Binary files, package-lock.json, screenshots/ and docs/dashboard/token-usage.json, refusals.json and gates.json are written by tools, not people, and are not counted. The first rule that matches a file’s path decides its box:

    1. Specs: plan.md and specs/, the template and README there included.
    2. Context: any other *.md (CLAUDE.md, READMEs, the PR template), .claude/ (the agents and settings), and docs/ apart from docs/dashboard/.
    3. Tests: a path through a test/ or tests/ folder (src/test/, the harness and its support/ included), or a file named *Test.java, *Tests.java, *IT.java, test_*.py, *_test.py, conftest.py, *.test.js or *.spec.ts and their kin.
    4. Scripts, CI, dashboard (drawn with the tests, as verification): the rest of scripts/, .github/ and docs/dashboard/.
    5. Production code: everything else: source, migrations, Dockerfiles, compose, .env.example, observability/, the frontend and data/ pipelines.

    The rules sort by path, and a path does not always say what a change was for. A spec-change PR that fixes a test counts as tests; a test helper under src/test/ counts as tests even when it is plumbing; a Markdown file inside a service counts as context; the dashboard’s own code counts as verification. The ratio of tests to code uses the Tests box alone, without the scripts and without tests/fixtures/.

    Refresh. python scripts/spec-drift.py --build in the repository writes this page with its data. It is rerun after every merge, before the next step starts.

    Limits. Names in a spec that should disappear (like a table leaving the module that owned it) still count as shared vocabulary. Comments are recognised by line (//, /*, *, --, #, <!--), not parsed, so a marker inside a string can hide the code after it on that line. The gap measures shared language, not correctness; correctness lives in the acceptance criteria and the tests.
